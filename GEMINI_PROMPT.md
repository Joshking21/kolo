# TASK: Build the Kolo web frontend (in `web/`)

You are building the **complete frontend** for **Kolo**, a group-savings app based on Nigerian **ajo/esusu**. A group of people pays a fixed amount every week or month, and each round one member collects the whole pot. Members also have a wallet they can fund and withdraw from.

The backend is being written **by hand, phase by phase**, as a learning project. It doesn't exist yet for most endpoints. So you'll build the frontend against a **mock API (MSW)** that behaves exactly like the real one. As each backend phase is finished, its part of the mock gets switched off and the UI talks to the real API with **zero code changes**. That only works if you follow the contract to the letter.

Work only inside `web/`. **Never create, edit or delete anything in `api/`**, or in `ROADMAP.md`, `API.md` or `docker-compose.yml`.

## 3. API client (`src/lib/api/client.ts`)

One function, `apiRequest<T>(method, path, { body?, query?, idempotencyKey?, signal?, skipAuthRefresh? })`. It must:

1. Prefix the path with `/api/v1`. Always use relative URLs, so the Vite proxy or MSW handles them.
2. Set `Content-Type: application/json` when there's a body, and `Accept: application/json`.
3. Attach `Authorization: Bearer <token>` if the token store has one.
4. Attach `Idempotency-Key` when `idempotencyKey` is given.
5. Attach `X-Request-Id: <uuid>` (`crypto.randomUUID()`).
6. Send with `credentials: "same-origin"` (the refresh cookie needs it).
7. Parse the response:
   - `204` → `undefined`
   - JSON otherwise
   - a non-JSON error body → `ApiError` with code `INTERNAL_ERROR`
   - a network failure (fetch throws) → `ApiError` with `status: 0` and code `NETWORK_ERROR`. **This is a client-only code. Never expect it from the server.**
8. On a non-2xx status, throw `ApiError { status, code, message, details, requestId, retryAfterSeconds }`. `retryAfterSeconds` comes from the `Retry-After` header.
9. **Silent refresh.** If the response is `401` with code `UNAUTHENTICATED`, and the request wasn't itself an `/auth/*` call:
   - call `POST /auth/refresh`, **single-flight**: many concurrent 401s share one refresh promise
   - store the new token, and retry the original request **once**
   - if the refresh fails, clear the session, send the user to `/login?next=<current path>`, and throw the original error.
10. Record every request in the dev log (§12): method, path, query, request headers (with `Authorization` shown as `Bearer eyJ…<last 6 chars>`), request body, status, response headers, response body, duration in ms, whether MSW served it, and whether `Idempotent-Replayed: true` was present.
11. Apply the dev-panel settings:
    - **Slow network** adds 1500 ms before sending.
    - **Double-send money requests** (only for requests with an `idempotencyKey`) fires the *identical* request twice at the same time with the same key, logs both, and returns whichever resolves first with a 2xx (or the first error if neither succeeds).

## 4. Auth (`src/lib/auth/`)

- The access token lives **in memory only** (a module variable in `token-store.ts`). **Never put tokens in localStorage, sessionStorage or cookies from JavaScript.**
- When the app starts, `AuthProvider` calls `POST /auth/refresh` (with `skipAuthRefresh`):
  - Success → status `authenticated` with the user.
  - `REFRESH_TOKEN_INVALID` → status `anonymous`.
  - While it's pending, render a full-screen splash: the Kolo wordmark centred, with a 20px spinner under it, on `--color-bg`. No layout shift when it disappears.
- `useAuth()` returns `{ status: "loading" | "authenticated" | "anonymous", user, login(email, password), register(input), logout(), logoutAll(), refreshUser() }`.
- `logout()`:
  1. calls `POST /auth/logout`
  2. clears the token
  3. **clears the whole React Query cache**
  4. goes to `/login`.
- **Route guards:**
  - `/app/*` requires `authenticated`. Anonymous users go to `/login?next=<path>`.
  - `/login` and `/register` send authenticated users to `/app`.
- After login or registration, go to `next` if it's a safe relative path starting with `/app`; otherwise go to `/app`.

## 5. Data fetching rules (`src/lib/query-client.ts`)

Default query options:
- `staleTime: 15_000`
- `refetchOnWindowFocus: true`
- `retry`: **0 for any `ApiError` with status 400–499**; up to 2 for network errors and 5xx (exponential backoff)
- Mutations **never** retry automatically.

Query keys (use a factory; don't write keys inline):
```
["me"]
["wallet"]
["wallet", "transactions"]                   (useInfiniteQuery)
["wallet", "deposits", depositId]
["wallet", "withdrawals"]                    (useInfiniteQuery)
["banks"]                                    (staleTime: Infinity)
["groups"]
["groups", groupId]
["groups", groupId, "rounds"]

["ledger", transactionId]                    (staleTime: Infinity; ledger transactions never change)
```

What to invalidate after each mutation:
| Mutation | Invalidate |
|---|---|

| contribute | `["wallet"]`, `["wallet","transactions"]`, `["groups"]`, `["groups", id]`, `["groups", id, "rounds"]`, `["groups", id, "activity"]`, `["notifications","unread-count"]` |

## 6. Helpers (each with unit tests)

### `money.ts`
- `formatKobo(kobo: number, opts?: { signDisplay?: "auto" | "always" | "never" }): string`
  - Uses `Intl.NumberFormat("en-NG", { style: "currency", currency: "NGN" })`.
  - **Whole naira shows no decimals; anything else shows exactly 2.**
  - Examples: `formatKobo(1250000)` → `"₦12,500"`, `formatKobo(1250050)` → `"₦12,500.50"`, `formatKobo(-100000, { signDisplay: "always" })` → `"-₦1,000"`, `formatKobo(0)` → `"₦0"`.
  - Use `−` (U+2212, the real minus sign) in the UI layer only if it's applied consistently. Otherwise keep `-`. Write down your choice in NOTES.md.
- `parseNairaToKobo(input: string): number | null`
  - Accepts `"12500"`, `"12,500"`, `" 12,500.5 "`, `"₦12,500.50"`, `"0.01"`.
  - Rejects (returns `null`): an empty string, more than 2 decimal places, negatives, letters, multiple dots, misplaced commas such as `"1,2,3"` (but `"1,234,567"` is fine), and anything above `Number.MAX_SAFE_INTEGER` kobo.
  - **Implement it with string operations only.** Split on `.`, pad the fraction to 2 digits, and join. **Never compute `naira * 100` with floats** (`0.29 * 100 = 28.999999999999996`). Include a test for `"0.29"` → `29` and `"1.10"` → `110`.
- `koboToNairaInput(kobo: number): string`: fills money inputs when editing. `1250000` → `"12,500"`, `1250050` → `"12,500.50"`.

### `dates.ts` (only `Intl` and `Date`; no libraries)
- `formatDate(iso)` → `"19 Nov 2026"`
- `formatDateTime(iso)` → `"19 Nov 2026, 9:30 am"`
- `formatRelative(iso, now = new Date())`:
  - `"just now"` (< 1 minute)
  - `"5 minutes ago"`, `"3 hours ago"`, `"yesterday"`, `"4 days ago"`
  - otherwise `formatDate`
  - for future times: `"in 3 hours"`, `"tomorrow"`, `"in 5 days"`.
- `formatDue(iso, now)`:
  - `"Due today"`, `"Due tomorrow"`, `"Due in 5 days"`
  - `"Overdue by 2 days"`, `"Overdue by 1 day"`.
- Every date is displayed in the user's local time zone. The tests must pin `now` and the time zone (`process.env.TZ = "Africa/Lagos"` in setup).

### `phone.ts`
- `normalizePhone("0803 123 4567")` → `"+2348031234567"`; returns `null` if invalid (rules in API.md §3).
- `formatPhone("+2348031234567")` → `"0803 123 4567"` (local display format).

### `invite-code.ts`
- `cleanInviteCode(" k7qm-2xpa ")` → `"K7QM2XPA"` or `null`.
- `formatInviteCode("K7QM2XPA")` → `"K7QM-2XPA"`.

### `idempotency.ts`: `useIdempotencyKey()`
Returns `{ key, renew }`. The rules, which explain why it exists:
- A key is created **when the user starts an action** (the confirm dialog opens) and stays the **same through every retry** of that action. That's what makes a retry after a timeout safe.
- `renew()` is called **only after a definite outcome**: success, or a 4xx that means "this exact request will never succeed" (`INSUFFICIENT_FUNDS`, `ALREADY_CONTRIBUTED`, `ROUND_NOT_COLLECTING`, `GROUP_NOT_ACTIVE`, `VALIDATION_ERROR`).
- On `NETWORK_ERROR`, 5xx or `IDEMPOTENCY_IN_PROGRESS`, **keep the key**. The "Try again" button reuses it.
- Closing and reopening a dialog creates a new key.
- Test all of this.

### `validation.ts`
Zod schemas for every form, matching API.md §3 **exactly**: same limits, same regexes. Field-level messages should be human:
- `"Enter your full name (at least 2 characters)"`
- `"Enter a valid email address"`
- `"Enter a Nigerian phone number, e.g. 0803 123 4567"`
- `"Use at least 8 characters, with a letter and a number"`
- `"Minimum contribution is ₦1,000"`
- `"Maximum contribution is ₦1,000,000"`
- `"Use whole naira (no kobo)"`
- `"Account number must be 10 digits"`

## 7. Mock API (MSW): it must behave like the real backend

The mock is not a pile of static JSON. It's a small **in-memory backend** that enforces every rule in API.md, so the UI is built against real behaviour (errors, edge cases, payouts).

### Starting it (`main.tsx`)
- Read `VITE_MOCK_DOMAINS`. If it's non-empty, start the MSW worker with **only those domains' handlers**, using `onUnhandledRequest: "bypass"`, so un-mocked `/api` calls go through the Vite proxy to the real API. **Wait for `worker.start()` before rendering.**
- Domain → handlers:
  - `auth`: `/auth/*`, `/me`, `/me/password`
  - `groups`: `/groups`, `/groups/*` (including rounds and contribute)
  - `wallet`: `/wallet`, `/wallet/transactions`, `/ledger/*`
  - `payments`: `/banks`, `/wallet/deposits*`, `/wallet/withdrawals*`, `/dev/fake-provider/complete`
  - `notifications`: `/notifications*`, `/groups/:id/activity`
  - `dev`: `/dev/fund-wallet`, `/dev/groups/*`, `/dev/jobs/*`
  - `/health` is never mocked.

### The mock database (`db.ts`)
- Tables mirror the real schema in ROADMAP Phase 1: users (with a plain-text `password` field; **it's a mock**, and add a comment saying so), accounts, ledgerTransactions, ledgerEntries, groups, groupMembers, rounds, contributions, deposits, withdrawals, notifications, activities, idempotencyKeys, refreshTokens.
- **Persisted to `localStorage`** under `kolo-mock-db-v1` after every write, and loaded when the page loads. If it's missing or corrupt, rebuild it from the seed.
- `resetMockDb()` rebuilds from the seed. The dev panel exposes it.

### The rules engine (`engine.ts`)
All mock handlers call the engine; the handlers only translate HTTP. The engine must:
- Post ledger transactions whose entries **sum to zero**. Throw if they don't.
- Compute balances as the sum of entries. Reject debits that would make a non-`allow_negative` account negative (`INSUFFICIENT_FUNDS`).
- Implement register (user + wallet), create/join/leave/cancel/start group (with positions and due dates exactly as API.md describes), contribute (with automatic payout on the last payment, round advance, group completion), dev fund, fake members, fake contributions, deposits (fake provider) and withdrawals (fake transfer).
- Create **activities and notifications** at the same moments the real backend will (see the types in API.md).
- Withdrawals progress on timers: `pending` → `processing` after 2 s → `succeeded`/`failed` after another 3 s. Account numbers ending in `0000` fail, and the money returns through a `withdrawal_reversal`.
- `runDueRounds(now)` implements API.md §5.
- `engine.test.ts` covers:
  - the ledger always sums to zero after a full group lifecycle
  - insufficient funds
  - double contribution
  - payout on the last payment
  - group completion
  - start with 1 member fails
  - join a full group fails
  - a failed withdrawal is reversed.

### HTTP behaviour (`http.ts`)
- **Latency:** a random 250–700 ms on every mocked response, so loading states are visible.
- **Auth:**
  - The mock issues **JWT-shaped** access tokens: base64url header and payload `{ sub, iat, exp }`, with a fake signature.
  - Mocked handlers read `sub` from the bearer token. A missing or expired token gets `401 UNAUTHENTICATED`.
  - Use a 15-minute expiry, like the real API, but the dev panel can trigger "Expire access token now" (§12) so silent refresh can be tested.
  - The refresh token is an HttpOnly-style cookie: set `kolo_rt_mock` with `document.cookie`, since a service worker can't set HttpOnly cookies. This is mock-only; leave a comment saying so.
- **If the token's `sub` isn't in the mock DB** (because `auth` is live but other domains are mocked), create a mock user with that id, the name "You", and a ₦0 wallet, then continue. This keeps mixed mock/live modes usable.
- **Idempotency** works exactly like ROADMAP Phase 5 describes:
  - store by (user, key)
  - same key + same body → replay with `Idempotent-Replayed: true`
  - different body → `422 IDEMPOTENCY_KEY_REUSED`
  - concurrent → `409 IDEMPOTENCY_IN_PROGRESS`
  - *Double-send* in the dev panel must visibly show one real response and one replay or 409.
- **Errors** use the exact envelope and add `X-Request-Id` to every response.
- **Pagination:** opaque base64 cursors.
- **Rate limiting:** for `POST /auth/login`, more than 5 failed attempts per email in 15 minutes → `429` with `Retry-After`.

## 13. Things that count as slop: don't do any of them

- Inventing endpoints, fields or error codes not in API.md, or "temporarily" hard-coding data in components instead of going through the API layer.
- Calling `fetch` anywhere except `client.ts`.
- `any`, `as unknown as`, `// @ts-ignore`, `eslint-disable` (if one is truly unavoidable, explain it on the same line).
- `console.log` left in the code.
- Floats for money, or computing kobo with `* 100`.
- Showing the server's raw `message` to users.
- Missing loading, empty or error states. Spinners where a skeleton belongs. Layout jumping when data arrives.
- Lorem ipsum, "John Doe", emoji in UI copy, fake stats or testimonials, stock-photo hero images, gradient blobs, glassmorphism, neon glows, or anything that looks like a real bank's or payment provider's branding.
- Copy that sounds like a template ("Unlock the power of…", "Seamless", "Revolutionise", "Effortlessly").
- Components over ~250 lines. Split them.
- Duplicated logic (money formatting, error mapping, query keys): there's exactly one source for each.
- Disabled buttons with no explanation. Every disabled primary action shows *why* (a hint or tooltip text).
- Tokens in localStorage.
- Any mutation of money that updates the UI before the server confirms it.
